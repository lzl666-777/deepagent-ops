# 审计为什么是确定性的

## 问题

原来的审计专员是一个 deepagents 子 agent，工具列表和"经营数据分析师"**逐字相同**：

```
list_sql_tables / get_table_data / execute_sql_query
calc_inventory_turnover / list_slow_moving_products / calc_gross_margin / calc_return_rate
```

所谓"独立复核"，实际是同一个模型、同一套工具、同一段算术，换个提示词再跑一遍，
然后让模型自己比较两份结论。模型算错的地方，第二遍还会算错——而且第二遍还会
很有信心地说"复核一致"。

实测（`evaluation/result.json`，15 条用例）：

| | |
|---|---|
| 审计触发次数 | **1 / 15** |
| 决策类通过 | 1 / 3 |
| C1 / C2 耗时 | 480.0s / 480.4s（超时，根本没走到审计） |

也就是说，这个项目最重要的卖点，在全套评测里只发生了一次。

## 现在

`verify_claims` 把"比较"从模型手里拿走：

```
报告里的数字 --(模型抽取)--> claims
                               |
数据库 --(collect_truth)--> Truth --(agent-audit)--> 逐项比对 --> 结论
```

模型只做它擅长的事：从报告里把数字读出来。数字对不对，由代码重算。

### 分层

| 模块 | 职责 | 是否碰 I/O |
|---|---|---|
| `tools/audit_core.py` | 检查项、严重程度、渲染 | 否（纯函数，可离线测） |
| `tools/audit_tools.py` | 从 MySQL 取基准值、包成 LangChain 工具 | 是 |
| `agent-audit`（独立仓库） | 比较、容差、公式求值、报告 | 否 |

### 独立性

审计**不 import** `business_tools`。那些工具正是被审计的对象；如果共用同一段查询，
一个 bug 会让两边同时算错、并且互相印证为"一致"。所以 `collect_truth` 自己写 SQL，
哪怕多几行。这不是重复代码，是独立实现。

### 严重程度

| 检查 | 级别 | 含义 |
|---|---|---|
| `truth(*)` | error | 报告的数 ≠ 数据库重算的数 |
| `consistency(gross_margin)` | error | 报告自相矛盾（毛利率与成本/售价对不上） |
| `threshold(SOP)` | warning | 真值越过 8% / 30% 红线 |
| `freshness(data_as_of)` | warning | 数据基准日过旧 |

`report.passed` 的含义是**"这些数字是真的"**，不是"这个结论是对的"。
把越红线判成 error，会让审计替分析师做业务判断，也会让真正想知道的
"数字是否可信"被噪声淹没。

红线按**真值**判、不按报告里的数判：分析师把 21.82% 少报成 8.2% 时，
告警必须说"真值 21.82% 越线"，而不是"8.2 超过上限 8"。

## 跑一下

```bash
python examples/audit_demo.py     # 不需要 MySQL / API Key
```

三个场景：如实报告（通过，但红线告警）、少报退货率（不通过，指出 21.82）、
百分数当小数（不通过，点名单位混用）。

## 已知边界

- **需要调用方给 `action` 式的结构化输入**：模型得把数字抽成 `claims`。抽错了（比如
  漏填一项）只会让那一项 `SKIP`，不会误判——但也不会被发现。
- **只有单一商品维度**：跨商品的对比（"比同类高 3 个点"）还不在检查范围内。
- **数字对 ≠ 结论对**：审计只保证数据是真的；结论是否合理仍由主 agent 负责。
- **评测需要重跑**：`86.7%` 与 `审计触发率 1/3` 是改动前的数字，改动后应重新执行
  `python -m evaluation.evaluate` 再看。
